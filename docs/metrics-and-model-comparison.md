# 검증 지표·모델 비교·ValidationError

작성일: 2026-10-16 KST. **현재 측정은 작은 개발셋의 애플리케이션 계약 검사다. 일반적인 에이전트 품질 점수는 아니다.** 실제 Qwen 평가와 실패 수정 기록을 추가했고, Astra API 경로·평가 명령은 준비했으나 실제 비교는 API 키 설정 전이라 실행하지 않았다.

## 어떤 검증을 하는가

- **정규식:** 기본 요청에서 지원 종목·기간·금지 범위를 해석한다. 정답 채점기나 근거 적합성 평가기가 아니다.
- **생성용 JSON Schema:** 모델에 허용된 필드·자료형·열거값을 전달한다. 연구 분기에서는 `action=research`, `message=null`을 명시한다.
- **Pydantic:** 실제 응답을 파싱하고 필드 간 업무 규칙, 중복 종목, 결과 상태와 인용 ID를 검사한다. Python `model_validator`의 모든 조건이 자동으로 JSON Schema에 옮겨지는 것은 아니다.
- **unittest:** 위 구현과 HTTP·API·재현·실패 처리의 회귀 검사를 실행한다. 현재 79개가 통과했다. 이 중 15개는 웹 조사 연결의 합성 응답 테스트이며, 실제 검색 품질 점수가 아니다. 기존 원격의 소스 import 경로 회귀 검사도 보존했다. 테스트 수는 모델이 맞힌 질문 수와 다르다.
- **개발용 평가기:** 고정 입력의 기대 상태·종목 집합·수익률·호출 수·오류 보존을 비교한다. 모델을 사용하는 평가에서는 출력 유효성·요청 일치도도 별도로 센다. 수익률 정답은 생산 계산 함수를 다시 호출하지 않고 별도 유리수로 작성했다.

BM25는 문서 검색의 순위 점수다. 확률이나 정답률이 아니며 질의·문서 집합에 따라 달라지므로 에이전트 품질 점수로 사용하지 않는다. 검색 품질을 평가하려면 질의별 정답 문서를 먼저 정하고 Recall@k·순위 지표 등을 별도로 측정해야 한다. 현재 그러한 정답 문서 평가셋이나 의미적 인용 적합성 점수는 없다.

## ValidationError의 실제 원인과 수정

[수정 전 실제 실패](validation/planner-v2/before-live-validation-error.json)에서 모델은 다음 두 필드를 동시에 생성했다.

```json
{"action": "research", "message": "Missing symbol or period: clarify."}
```

`ResearchPlan`의 Python 검증기는 research에 확인 질문용 message를 허용하지 않는다. 기존 JSON Schema는 이 조건을 표현하지 않았고, 기존 공통 프롬프트도 이미 지원 범위를 통과한 요청에 확인 질문 규칙을 함께 주었다. 형식상 JSON인 응답이 업무 조건을 위반해 Pydantic `ValidationError`가 발생했다. 해당 실행에서는 Binance 조회 전에 멈췄다. 동일 질문의 데모 실패 기록도 있어 live API의 문제로 볼 근거는 없다.

수정은 검증기를 약화하는 대신 생성용 스키마에 현재 연구 분기의 `message=null`을 반영하고, 프롬프트에 역할·예시·원인 질문 처리 기준을 명시했다. 같은 종목의 순서만 다른 계획도 허용한다. 잘못된 종목·기간·출력은 여전히 실패한다.

[수정 후 live 3종목](validation/planner-v2/live-three-symbols.json)은 `completed`, [원인 질문](validation/planner-v2/live-causal.json)은 `insufficient_evidence`가 됐다. 모델은 Qwen3:8B로 같고 프롬프트·생성 제약이 달라졌다. 과거 버전 전체 20개를 다시 측정한 결과는 없으므로 ‘0%→100% 개선’처럼 쓰면 안 된다. 두 실행의 시각·시장 자료도 달라 가격·지연의 수정 전후 비교 근거로 쓰지 않는다.

엄격 재현은 요청 본문까지 검사하므로 프롬프트·스키마가 바뀐 과거 모델 tape는 요청 불일치로 거부될 수 있다. 모델 응답 고정 재현과 새 모델/프롬프트를 실행하는 실험은 다르다.

## Astra 비교 실행 준비

공식 API 모델은 `gpt-6-astra`다. [공식 모델 문서](https://developers.openai.com/api/docs/models/gpt-6-astra)는 Structured Outputs를 지원하고 Standard 텍스트 단가를 입력 $10, 캐시 입력 $1, 출력 $50 / 100만 토큰으로 안내한다. 계정 접근 권한은 별도로 확인해야 한다. API 사용량을 이 대화나 Codex의 모델 선택 기능으로 대신 측정할 수는 없다.

키를 본인 터미널의 `OPENAI_API_KEY`로 설정한 뒤, 같은 프로젝트·같은 의존성 환경에서 실행한다. 키를 채팅·README·커밋에 넣지 않는다.

```sh
PYTHONPATH=src .venv/bin/python -m market_agent evaluate --planner baseline --output .market-agent/baseline.json
PYTHONPATH=src .venv/bin/python -m market_agent evaluate --planner ollama --output .market-agent/qwen.json
PYTHONPATH=src .venv/bin/python -m market_agent evaluate --planner openai --output .market-agent/astra.json
```

각 JSON 옆에 Markdown 요약을 생성한다. 서버에서 사용하려면 같은 키가 설정된 터미널에서 서버를 시작해야 한다. 다른 셸에 export해도 실행 중인 서버의 환경변수는 바뀌지 않는다.

두 모델의 질문·합성 일봉·문서·업무 규칙·코드 버전을 같게 유지한다. 현재 비교는 사전 검사된 15개 연구 계획에 대한 통합 결과이며, 애매한 요청까지 포함한 독립적인 모델 계획 능력 평가가 아니다. 토큰 수는 토크나이저가 달라 그 자체로 품질 우열을 뜻하지 않는다.

OpenAI 요청은 [Responses Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)를 사용한다. 모든 출력 필드를 required로 만들고 nullable 값은 null로 표현한다. reasoning low·최대 출력 1,024토큰은 이번 연결의 초기 비용 제한 가정이며 최적값이 아니다. Qwen의 think=False와 같은 추론 연산량이라는 뜻도 아니다. 제한에 걸린 응답은 실패로 세고 관측 사용량은 보존한다.

비용은 보고된 입력·출력·캐시 입력 토큰에 날짜가 있는 Standard 단가를 적용한 추정이다. 추론 토큰을 출력 토큰에 중복 가산하지 않는다. 캐시 쓰기 할증·기타 수수료·세금·운영 비용은 제외하며 실제 청구액이 아니다. 누락 사용량은 null로 남긴다. **현재 Astra는 모의 응답 경계 테스트만 통과했고 실제 호출·성능·비용은 미측정이다.**

비교 제안은 8/10이다. 같은 조건에서 품질과 비용을 함께 비교하는 방향은 타당하다. 다만 현재 개발셋은 고정 흐름도 전부 통과하므로 모델의 추가 가치를 구분하기 어렵다. 다음에는 새 동결 사례와 사람의 근거 적합성 검토로 변별력을 확보해야 한다. 자동 합격 점수나 임의의 종합 점수는 만들지 않는다.

## LangChain·LangGraph를 넣지 않은 이유

첫 버전의 실제 흐름은 조건 검사 → 한 번의 계획 → 정해진 도구 실행 → 계산·결과 생성이다. 고정된 함수와 분기만으로 설명·검사할 수 있어 별도 오케스트레이션 의존성을 넣지 않았다. 프레임워크를 쓰면 품질이 오르거나 쓰지 않으면 더 빠르다는 실험 결과는 없다.

[LangGraph 공식 설명](https://docs.langchain.com/oss/python/langgraph/overview)은 상태를 유지하는 장기 실행, durable execution, 체크포인트·재개, human-in-the-loop 등을 주요 기능으로 제시한다. LangChain 없이도 사용할 수 있다. 현재 JSON 기록·처음부터의 HTTP 재현은 중단 지점부터 이어 가는 durable execution과 같지 않다.

긴 실행의 중간 재개, 승인 대기, 동적 분기·반복의 상태 관리가 실제로 필요해지면 LangGraph 도입이 합리적이다. 프레임워크가 이번 출력 계약 오류를 자동으로 고쳐 주지는 않는다. 지금 저장소는 범용 자율 에이전트가 아니라 제한된 연구 워크플로우와 선택형 모델 계획의 첫 버전이다.

## 지원서에 쓸 수 있는 문장

> 고정 합성 데이터 기반 시장 조사 워크플로우에 정상·부분 장애·지원 불가·근거 부족을 포함한 20개 개발 시나리오와 독립 수치 기대값을 구성했습니다. 실제 Qwen3:8B 계획 호출 15건을 포함한 실행에서 20/20 시나리오가 기대 계약을 충족했으며, 사용 중 발견한 계획 스키마 충돌을 수정하고 지연·토큰·실패 기록을 공개했습니다.

AI 보조 구현과 본인이 직접 검토·수정한 범위는 별도로 밝힌다. ‘범용 에이전트 정확도 100%’, ‘Astra 대비 우수’, ‘운영비 0원’은 현재 증거로 쓸 수 없다.
