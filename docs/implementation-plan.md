# 구현 구조와 다음 단계

현재 live 연구 평가와 기본 실행은 [새 평가 기준](live-research-evaluation.md)을 따른다. 아래 합성 데이터·계획 추출 측정은 보존한 개발 기록이며 `regression`으로만 실행한다.

**첫 버전은 고정 Python 흐름 하나에 CLI·API·웹 콘솔·재현·평가를 연결했다.** LangGraph·React·MCP 없이 현재 필요한 경계를 구현했다.

```text
__main__.py (CLI) ─┐
api.py → web/ ─────┴→ runtime.py
                      │  baseline_plan 또는 Ollama 계획 검증
                      │  종목별 조회 → 문서 검색 → 근거 검사 → 결과
                      ├→ tools.py + schema.py
                      ├→ llm.py (기존 계약 유지)
                      └→ records.py → 실행별 JSON
                             ↑
               replay_run → ReplayTransport (외부 호출 없음)

evaluate.py → 같은 runtime.py → 독립 기대값 검사 → 원시 평가 JSON
```

## 구현한 경계

`tools.py`는 한 종목의 완료 일봉을 검증하고 계산한다. `runtime.py`가 종목별 실패를 보존하며 순서대로 조회한다. 시장 조회를 다시 시도하거나 추가 문서 조사에서 재호출하지 않는다.

문서는 원 `Source`를 보존한 작은 BM25 인덱스로 검색한다. 무일치일 때 알려진 캔들·UTC 표현이 있으면 `klines UTC`로 한 번만 재질의한다. 검색어를 바꿀 근거가 없으면 종료한다. 의미 기반 검색이나 개방형 리서치 루프가 아니다.

기본 요청 해석은 보수적인 한·영 규칙이다. Ollama 옵션은 이미 지원 가능한 연구 요청에서만 실행하며, 모델 계획의 종목·기간·행동이 요청 계약과 다르면 오류로 종료한다. 모델이 과제를 임의 확장하지 않게 한 첫 버전의 제한이다. LLM 사용이 완료율을 높였다는 증거는 아직 없다.

`records.py`는 외부 요청 메서드·전체 URL·본문·순서를 기록한다. 문서 자료도 스냅샷으로 저장한다. 재현은 동일 조사 함수를 실행하고 모든 기록의 소비를 확인한다. 저장된 결과를 그대로 반환하는 동작과 구분한다.

프론트엔드는 빌드 단계 없는 HTML/CSS/JavaScript다. 화면에 서버의 문자열을 넣을 때 `textContent`를 사용한다. Python 수치 표시값을 그대로 사용해 브라우저 부동소수점 재계산을 피한다.

## 유지한 설정과 근거 수준

기존 `qwen3:8b`, `temperature=0`, `think=False`, `keep_alive=10m`을 유지했다. 최대 수집 두 라운드는 기존 프로젝트의 초기 운영 가정이다. 3개 종목은 HTTP 3회이며, 추가 문서 검색과 별개다.

시장 HTTP timeout 10초·Ollama timeout 300초·문서 `top_k=2`·가격 정밀도 40자리·질문 최대 2,000자는 **이번 첫 버전의 운영 가정**이다. Binance 서버의 10초 처리 제한이 클라이언트 timeout의 최적값을 입증하는 것은 아니다. 전체 실행 마감 시간이 구현된 것도 아니다. BM25 `k1=1.5`, `b=.75`는 기존 학습 코드의 기본값을 참고했다. 모두 실제 오류·지연·검색 적합성을 측정해 조정할 값이다.

개발용 20개는 구현했다. 동결 평가 40개·반복 3회는 이전 제안으로만 남기며 자동 기본값으로 쓰지 않는다.

## 다음으로 가치 있는 작업

1. 본인이 실행 경로를 설명하고 작은 변경을 직접 수행한다. AI가 작성한 코드를 이해한 증거가 먼저다.
2. 실제 사용자의 반복 과제 하나를 관찰하고 입력·결과 범위를 좁힌다.
3. 사용 중 발견한 실제 실패를 기록하고 두 코드 버전을 같은 자료로 비교한다. 합성 장애를 과거 운영 사고로 포장하지 않는다.
4. 새로 동결한 자료로 실제 모델의 요청 해석·근거 적합성을 평가한다. 고정 흐름과의 차이를 측정한 뒤 도구 선택 에이전트를 결정한다.
5. 공개 데모를 배포할 때 인증·자원 제한·비밀 관리 등 필요한 운영 경계를 설계한다. 현재 로컬 서버를 그대로 외부에 노출하는 단계는 아니다.

## 계획 계약 수정과 OpenAI 연결 준비

실제 사용 중 발견한 research/message 충돌을 생성용 JSON Schema의 research 분기와 null message 제약·명시적 프롬프트로 수정했다. 일반 ResearchPlan의 업무 검증은 유지한다. 종목 순서만 다른 계획은 허용한다. OpenAI Responses 경계를 HTTPX로 추가했으며 별도 SDK·프레임워크 의존성은 넣지 않았다. GPT-6 Astra의 reasoning low·최대 출력 1,024토큰은 비용을 제한하기 위한 초기 가정이다. 공식 지원 옵션이라는 것과 이 과제의 최적값이라는 것은 다르다. 실제 모델에 관한 분모·사용량·제약은 [지표 문서](metrics-and-model-comparison.md)를 따른다.

## 선택형 외부 웹 조사

`web=true`, `mode=live`, `planner=openai`는 기존 가격 계획 생성과 별도 분기다. 선택적 Binance 수치 수집 → OpenAI hosted search/read와 보고서 → 제공자 인용 형식 검증 → 결과·기록 순서다. 가격을 요구하지 않는 뉴스·거시 질문도 받는다. 앱이 자체 검색 엔진·기사 크롤러·범용 행동 루프를 구현한 것은 아니다. 호출 예산의 공식 정의, 초기 가정과 검증 한계는 [웹 조사 문서](web-research.md)에 있다.
